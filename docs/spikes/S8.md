# S8: Assistant bridge transport in the live window

**Verdict: Pass, with five K3 changes.** In the live window, the two-socket line transport works:

- A stream socket stays usable through 10 minutes awake with no agent data, then delivers data in 18 ms. That holds with 20 s pings on a pending read, and with no read pending at all. A read that is pending for 30.0 s with no data fails.
- A 5 MiB burst arrives complete and in order.
- 100 send connections take 35 ms in total.
- One socket can be written while a read on it is pending.
- `hc kill` gives a clean exit when the bridge finishes its shutdown within about 0.5 s.
- A bridge exits 267 ms after its watched pid dies.

The five K3 changes come from limits found on the way: a 30 s read timeout, `hc kill`'s 1 s escalation, a 1 MiB cap per write, a cap of 1,024 outstanding host tasks, and a default `hc` parent inherited from Herdr's environment. They are listed in "Consequence for K3" below.

**Sleep during the run.** The Mac went to sleep at 07:39:56 KST ("Software Sleep", lid closed, on battery; `pmset -g log`) during the first 10-minute run. From then until the lid was opened at 11:57:21 KST, work ran only in short DarkWake windows. The 10-minute item was measured again after that, fully awake (no sleep event between 02:57:21 and 03:08:21 UTC).

Run 2026-11-23 (KST) in the live Herdr 0.1.16 window (`hc` 0.1.21, macOS 27.0, Node 26.13.0). Throwaway mod `lz-spike`, hub copy in tab `lz-hub` of space `lazuli-spike`. Times below are UTC, as in the logs.

## Question

K3 plans one bridge per profile: a Node process started with `hc run --bg` that speaks line JSON on `127.0.0.1`. The mod talks to it over one long-lived stream socket and one short connection per send. Before building it, S8 checks in the live window:

1. Does a stream socket that sits idle 10 minutes still receive data?
2. Does a 5 MiB burst arrive in order?
3. How long do 100 send connections take?
4. Can one socket be written while a read on it is pending?
5. Does `hc kill` give a clean exit?
6. Does the bridge exit when the pid it watches dies?

## Setup

All of it lived outside the repository and is removed (see Cleanup).

- **Mod** `~/.config/herdr-app/mods/lz-spike/`:
  - `mod.json` `{"place":"none"}`.
  - `main.js`: a hub view. Every 500 ms it reads `data/lz-spike/ctl.json` and runs each listed op once in a `cx.spawn` task, writing `data/lz-spike/out/<id>.json`.
  - Ops: `hc`, `ppid`, `watch`, `idle`, `idlePing`, `idleNoRead`, `rtimeout`, `burst`, `sends`, `rw`, `diag`, `send`.
  - The sockets are `net.connect("127.0.0.1", port)` with a byte-level line framer, as `file/pdf-client.js` does it.
- **Stand-in bridge** `mods/lz-spike/bin/bridge.mjs`. It is K3 cut down to the transport:
  - `--profile --cwd --discovery --log --herdr-pid --idle-min --ping-ms --agent -- argv`.
  - The agent child is spawned `detached` (own process group). The bridge sends `initialize` once.
  - It writes the discovery file atomically (0600) after `initialize`. The server listens on `127.0.0.1:0` with a 64-hex token on the first line.
  - Ops `stream` (hello, then `{seq, at, msg}` per agent line), `send`, `shutdown`, plus a spike-only `echo` (echoes each later line; a `tick` after 3 s of silence).
  - Ping after `--ping-ms` of stream silence. A `process.kill(herdrPid, 0)` watch every 1 s. Idle exit.
  - SIGHUP, SIGTERM and SIGINT take the shutdown path. With a running prompt, that path is `session/cancel` and a wait of up to 3 s, then SIGTERM to the agent group, then SIGKILL after 2 s, or after 5 s when a cancel was sent. Then the discovery file is deleted and the bridge exits 0.
- **Stand-in agent** `mods/lz-spike/bin/agent.mjs`:
  - Answers `initialize` and holds `session/prompt`.
  - Echoes other requests (`spike/ping` → a result with the same id).
  - On `spike/burst {bytes}`, writes numbered lines of 60 B to 1 MiB, mixing 1-, 3- and 4-byte UTF-8 (`한글😀abc-`), each with its UTF-16 length and a code-unit checksum. It ends with `spike/burst-end {count, bytes}`.
  - `--ignore-cancel` and `--ignore-term` simulate a stuck agent. SIGHUP is logged and ignored. After stdin closes, the stand-in agent exits after 60 s, so an orphan stays visible but cannot linger.
- **Launch** from the hub, the K3 form: `hc(["run","--bg","--json","--no-parent","--no-notify","--cwd",dir,"--label","lz-spike.s8=<p>","--","/opt/homebrew/bin/node",bridge,…])`. The first three launches had no `--no-parent --no-notify` (see Evidence 7).
- **Herdr pid** from the hub: `exec("/bin/sh", ["-c", 'echo "$PPID"; ps -o pid=,ppid=,pgid=,comm= -p "$PPID"'])` gave `83420     1 83420 /Applications/Herdr.app/Contents/MacOS/Herdr`. K3's rule ("the Herdr pid is `$PPID` of an `exec`'d shell") holds.
- **Process layout** (`ps -o pid,ppid,pgid`): each bridge is a child of `herdr-core hold` (1121) and leads its own group. Its agent leads a separate group.

## Evidence

### 1. Stream socket idle, then data

**No pings, a read pending** (`idle1`, bridge `--ping-ms 0`). The stream read started at 22:29:02.331. It rejected after 30.0 s:

```
idle1: {"startedAt":1795386542328,"endedAt":1795386572333,
        "result":{"error":"socket read failed: Resource temporarily unavailable (os error 35)"}}
bridge: 22:29:02.331Z stream 1 (lz-spike) since 0
        22:29:32.339Z stream 1 closed
```

The next check shows whether the timeout itself closed the socket.

**The socket survives a failed read** (`rt2`, `--ping-ms 0`):

- A raw `sock.read(65536)` with no data rejected with the same EAGAIN (os error 35). This run spanned a system sleep, so it took 592.9 s instead of 30 s.
- A second `read()` on the same socket then returned the agent line, sent 3 s later: `{"ms":3147,"got":109,"text":"{\"seq\":1,…\"id\":\"rt2:1\"…"}`.
- A `write()` afterwards resolved in 0 ms.

The 30 s figure is therefore a per-read receive timeout; the connection stays up. [INFERENCE] In `idle1`, the socket closed because the op ended and QuickJS freed the socket object at once (reference counting).

**20 s pings, a read always pending** (`idlep1`, the K3 shape, bridge `--ping-ms 20000`):

- Awake from 22:33:31.9 to the sleep at 22:39:56: pings every ~20 s (`first: [20881, 40897, 60911]` ms), no read error.
- The Mac then slept. At a DarkWake 24 minutes later (23:04:06), the same socket still delivered data: the bridge's `bye {reason: "idle"}` at 1,834 s, then EOF. The bridge's 30-minute idle clock counts sleep.
- Result: `"pings":{"count":21,…,"maxGapMs":877793}`, `"readCalls":24`, `"failure":{"sinceStartMs":1834243,"error":"eof"}`. The 14.6-minute gap between pings was system sleep, and no read timed out across it.

**10 minutes awake**, both started at 02:58:21 UTC after the lid was opened:

- `idlep2` (bridge D, `--ping-ms 20000`, a read always pending, no agent data for 600 s):

  ```
  {"idleMs":600000,"failure":null,"readCalls":32,
   "pings":{"count":29,"first":[20112,40133,60151],"last":[540568,560586,580606],"maxGapMs":20112},
   "after":{"sinceTriggerStartMs":18,"sinceStreamStartMs":600021,"v":{"seq":1,"id":"idlep2:1"}},
   "second":{"sinceTriggerStartMs":2,"v":{"seq":2,"id":"idlep2:1-2"}}}
  ```

  29 pings at 20.0 s spacing, no read error. The first agent line after 600 s arrived 18 ms after its send began; a second one took 2 ms.

- `idleNoRead` (bridge C, `--ping-ms 0`, no read pending for 600 s): after 600,002 ms a send went out, and the first `read()` returned that line in 8 ms (16 ms after the send began). The idle loopback connection was not dropped in 10 minutes. Only a *pending read* has the 30 s limit.

### 2. A 5 MiB burst

| stream bytes | 5,683,317 | 5,684,427 |
| lines (3,000 chunks + end) | 3,001 | 3,001 |
| largest line | 1,048,715 B | 1,048,715 B |
| first line after trigger | 4 ms | 1 ms |
| last line after trigger | 139 ms | 134 ms |
| throughput | 39.0 MiB/s | 40.5 MiB/s |
| `read()` calls | 281 | 198 |

### 4. Writing while a read is pending

Spike op `echo` on one socket (`rw2`). In each round, a `read()` was started and left pending for 300 ms, then a line was written on the same socket:

```
size 10 B      ×3: write resolved 0–1 ms,   pending read resolved with the echo 1–3 ms after the write began
size 64 KiB    ×3: write 2–3 ms,            read 3 ms
size 1,040,000 ×3: write 23–32 ms,          read 25–34 ms
```

The read was pending at every write (`pendingAtWrite: true`), and no write waited for a read. A round with a 1 MiB pad (line 1,048,592 B) failed in `rw1`: `socket write exceeded the 1048576 byte limit`.

**Sockets are independent** (`diag2`). Bridge C's stream had a read pending (the "blocker"). In the same copy and the same milliseconds, a stream on bridge B opened, a send connected, wrote and got `{ok:true}`, and B's stream read the echo; each step took 0–1 ms. The blocker's read rejected later with the same os error 35.

### 5. `hc kill`

`hc(["kill", address])` from the hub. Seven kills:

| bridge state | `hc kill` returned after | bridge log | `hc` result |
|---|---|---|---|
| no running turn, agent obeys SIGTERM (5 bridges) | 56–109 ms | SIGHUP → `bye` → SIGTERM to agent group → agent exit → discovery deleted → `exit 0, 21–28 ms after the shutdown began` | `exit_code 0, reason "killed"` |
| no running turn, agent ignores SIGTERM (t61) | 1,045 ms | SIGHUP 22:28:25.108, bye, SIGTERM to the agent group, **SIGTERM to the bridge 25.610**, then SIGKILL | `signal 9`; agent orphaned; discovery file left |
| a running prompt, agent ignores `session/cancel` (t6h) | 1,026 ms | SIGHUP 02:59:30.072, `shutdown (signal); running 1`, cancel sent, **SIGTERM to the bridge 30.574**, SIGKILL ~31.079 | `signal 9`; the client got **EOF without `bye`**; agent `PPID 1` and alive; `s8e.json` left |

`hc kill` is "hangup, then terminate, then kill" (`hc schema`, `terminal.kill`). Measured: SIGHUP, SIGTERM about 500 ms later, SIGKILL about 1,000 ms after the SIGHUP. Because the agent leads its own process group, `hc kill`'s group signals never reach it: only the bridge can end it, and a SIGKILLed bridge leaves it running.

### 7. Found on the way

- **`hc` parent from Herdr's environment.** The Herdr app (pid 83420) carries `HC_TERMINAL_ID=t2h`, `HC_SCOPE` and `HC_TERMINAL_SOCKET` in its environment (`ps eww`). It was evidently started from a Herdr terminal. So a mod's `hc(["run","--bg",…])` without `--no-parent` got `"parent":"t2h","die_with_parent":true,"notify":true`: it dies with that terminal's program, and `hc` types notes into that agent. With `--no-parent --no-notify`, the result is `"parent":null,"die_with_parent":false,"notify":false`. S5 saw no parent because Herdr had been started differently then [INFERENCE].
- **Outstanding host tasks: at most 1,024 per runtime.** The first `burst` op wrapped each line read in `Promise.race([read, cx.sleep(60000)])`. During the 5 MiB burst this created about 1,000 pending timers. The next host call failed: `fs.writeFile(path, contents) exceeded the per-runtime outstanding host task limit of 1024`. After that the hub's poll loop stopped taking ops until reload. [INFERENCE] `cx.spawn` threw inside a timer callback, so the busy flag was never cleared.
- **`close()` can take effect late.** In `diag1` and `diag2`, `close()` on a send socket was called 500 ms after its reply arrived. The bridge saw that close only at the next event on another socket: when the stream closed 532 ms later (`diag1`), and when the blocker's read failed (`diag2`, across a sleep). When `close()` directly followed the reply read (`sends`), the bridge saw it within 1 ms. The bridge `end`s send sockets itself, so K3 does not depend on it.
- **Mod file writes are confined.** `fs.writeFile("/tmp/lz-spike-s8/out/…")` failed: `… is outside every granted write root; add its directory to capabilities.fs.write in the manifest`. Writes under `data/lz-spike/` worked. K3's runtime folder is written by the bridge (Node), not the mod.
- **Sleep counts as idle.** The bridges' 30-minute idle clock is wall time. After the Mac had slept past it, all three bridges exited for `idle` at the first DarkWake (23:04:06), with `exit 0, 198–228 ms after the shutdown began`.

## Consequence for K3

1. **Ping well inside the 30 s read timeout.** Every `read()` that sees no data for 30 s rejects with `socket read failed: … (os error 35)`.
   - Ping after **10 s** of stream silence, not 20 s. With the 1 s check that is at most 11 s between lines, leaving a margin of 19 s (about two-thirds of the timeout) for a busy bridge event loop, for a coalesced flush, and for the client's own scheduling. 20 s leaves 9–10 s, which a stalled bridge or a large flush can eat.
   - The client treats os error 35 on the stream as "nothing yet" and reads again on the same socket; the socket stays usable.
   - It declares the bridge lost only after 3 reads in a row fail that way, about 90 s without even a ping, or on EOF.
2. **Make the signal path fit `hc kill`'s 1 s.** `hc kill` sends SIGHUP, then SIGTERM at about +0.5 s, then SIGKILL at about +1 s. K3's 3 s cancel wait and 2/5 s SIGKILL timers cannot run under it. Split the paths:
   - **`{op:"shutdown"}`** (folder change, Retry, reaping a bridge that still answers) keeps K3's full path: cancel, wait up to 3 s, SIGTERM, SIGKILL; exit within 11 s. The mod uses it first and waits for the pid to go.
   - **SIGHUP, SIGTERM, SIGINT and Herdr gone** run a fast path within 400 ms: delete discovery, send `bye`, send `session/cancel` and SIGTERM to the agent group at the same moment, SIGKILL the group at +300 ms, exit 0. Measured with an agent that exits on SIGTERM: 21–28 ms.
   - `hc kill` is the mod's fallback for a bridge that does not answer `shutdown` within 5 s. After it, the mod also SIGKILLs the agent group (`-agentPgid`) if the dead bridge left one. That group id is the agent's pid, so discovery should carry `agentPid`.
   - Herdr gone: within 5 s with or without a running turn (detected in ≤ 1 s, fast path ≤ 0.4 s). The 12 s case disappears.
3. **Send lines over 1 MiB in pieces.** `sock.write` refuses more than 1,048,576 bytes per call. The client splits a `send` line into ≤ 1 MiB `write()` calls; the bridge already reassembles by newline. The 16 MiB line limit stays. The stream side is unaffected: one `read(1048576)` returned up to 736,812 bytes. Use `read(1048576)`: 30% fewer calls than 64 KiB for the same burst.
4. **Stay far below 1,024 outstanding host tasks per runtime.**
   - One pending `read()` per socket.
   - No timer per line or per read. A stalled read fails by itself after 30 s; use one watchdog per connection at most.
   - At most 8 parallel send connections per profile, queued. 100 in parallel worked (26 ms) but holds about 300 tasks.
   - Coalescing (K4: one `store.set` per session per 80 ms) uses one timer per session, not one per line.
   - Decoding cost in the copy: 3,001 lines in 257–459 ms, checksums included [INFERENCE: parsing alone is cheaper], so a 5 MiB burst must not be parsed inside one render.
5. **Launch with `--no-parent --no-notify`.** The launch becomes `hc(["run","--bg","--json","--no-parent","--no-notify","--cwd",folder,"--label","lazuli.assistant=<profile>","--",node,bridge,…])`. Without these flags, a Herdr started from a Herdr terminal makes that terminal the bridge's parent: the bridge would die with that terminal's program, and `hc` would type notes into it. `sys/runner.js` and `sys/sidecars.js` launch the same way and are exposed too (outside this slice).

Kept as designed:

- **Two channels.** One socket can be read and written at once, but K3's stream plus short send connections already works, costs ≤ 1 ms per send and is simpler to reconnect. Per K3, S8 only records this.
- **The 1 s Herdr-pid poll**: 243 ms to detection here.
- **Line JSON with a byte framer**: 3,000 mixed UTF-8 lines arrived intact.
- **The idle exit.** Because sleep counts toward the 30 minutes, after a long sleep the mod finds `bye {reason:"idle"}` or EOF plus a deleted discovery file, and relaunches through `open` as after any bridge exit.
